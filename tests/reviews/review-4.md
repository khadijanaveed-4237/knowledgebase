## New Findings (Cycle 4)

The following findings are from the Cycle 4 independent deep review, incorporating the assignment-reviewer subagent's evidence-based inspection and the primary agent's independent verification. Each finding cites exact evidence with `path:line` references and quoted text.

### AR-001 — Major — Overlapping responsibilities between kb-architect, kb-editor, and kb-tech-lead

- **File**: `.opencode/agents/kb-architect.md`, `.opencode/agents/kb-editor.md`, `.opencode/agents/kb-tech-lead.md`
- **Evidence** — From `kb-architect.md:16-36`, the Architecture Focus covers: Knowledge Base Structure, Content Organization, Consistency and Standards, Scalability and Maintainability, Relationships and Navigation. From `kb-editor.md:18-34`, the Review Focus covers: Documentation quality and best practices, Potential issues and edge cases, Performance and maintainability, Security considerations. From `kb-tech-lead.md:18-41`, the Review Focus covers: Technical Quality, Architecture and Design, Code and Database Practices, Security and Reliability, Maintainability and Standards.
- **Overlap areas**: Security considerations appear in `kb-editor.md:38` ("Identify exposed credentials, secrets, or sensitive information") and `kb-tech-lead.md:33` ("Check for insecure practices and exposed sensitive information"). Maintainability/standards appear in `kb-architect.md:33-36` and `kb-tech-lead.md:38-41`. Technical quality is covered by both `kb-editor.md:30-34` and `kb-tech-lead.md:18-21`.
- **Explanation**: These three agents cover significant overlapping territory. A user reviewing documentation might consult multiple agents and receive partially redundant feedback. The assignment-reviewer also flagged this as AR-001 (Major).
- **Severity**: Major — Seriously impairs usability; likely to cause wrong behavior or significant confusion about which agent to consult for documentation review tasks.
- **Recommended fix**: Consider clarifying each agent's distinct scope or consolidating shared areas, as noted in the assignment-reviewer's findings.

### AR-002 — Major — Assignment-reviewer scope does not explicitly cover PKM vault content

- **File**: `.opencode/agents/assignment-reviewer.md`
- **Evidence** — From `assignment-reviewer.md:28-33`: "Review both of these folders recursively: `.opencode/agents/` and `.opencode/skills/`. Inspect every agent and every skill. List each file you actually read. Do not imply coverage you did not perform."
- **Gap**: The assigned scope reviews `.opencode/agents/` and `.opencode/skills/` only. However, multiple skills reference paths inside the `pkm/` vault: `pkm/Knowledge/` (knowledge-linker SKILL.md:22), `pkm/Templates/` and `pkm/Ideas/` etc. (pkm SKILL.md:43-50). The review scope does not explicitly include inspecting the PKM vault content itself, creating a gap where issues inside the vault relevant to skill functionality may be missed.
- **Explanation**: The assignment-reviewer noted this as AR-002 (Major). Skills that reference PKM vault paths (knowledge-linker, pkm) were inspected via their instructions, but the review scope itself does not explicitly include the vault content. Users relying on this review may assume the PKM vault has been vetted, but the review explicitly does not cover vault content, which is central to the pkm and knowledge-linker skills.
- **Severity**: Major — Seriously impairs correctness and usability; users may assume the vault has been vetted when it has not been.
- **Recommended fix**: Extend the assignment-reviewer scope to explicitly include PKM vault content, or add a note that the vault is out of scope.

### AR-003 — Minor — Path references in skills are relative to PKM vault root, which could cause confusion

- **File**: `.opencode/skills/knowledge-linker/SKILL.md`, `.opencode/skills/pkm/SKILL.md`
- **Evidence** — From `knowledge-linker SKILL.md:22`: "Reads knowledge notes from `pkm/Knowledge/`". From `pkm SKILL.md:43-50`: The template table maps `pkm/Templates/ideas.md` → `pkm/Ideas/`, `pkm/Templates/knowledge.md` → `pkm/Knowledge/`, etc. These paths are correct relative to the PKM vault root but are not relative to the `.opencode/` project root. Users might confuse the two path bases (vault root vs. project root).
- **Explanation**: The assignment-reviewer flagged this as AR-003 (Minor). A user might incorrectly assume `pkm/Knowledge/` refers to a directory inside the `.opencode/` project structure rather than the PKM vault's internal structure.
- **Severity**: Minor — A real but limited defect with modest impact. A user might misinterpret the path structure, but the skill functionality is not impaired.
- **Recommended fix**: Add a note at the top of each skill's SKILL.md clarifying that `pkm/` paths refer to the PKM vault, not the project root.

### AR-004 — Stylistic — Agents use different output organizations appropriate to their purpose

- **File**: `.opencode/agents/assignment-reviewer.md`, `.opencode/agents/chaos-tester.md`, `.opencode/agents/project-detective.md`, `.opencode/agents/what-if-simulator.md`, `.opencode/agents/kb-architect.md`, `.opencode/agents/kb-editor.md`, `.opencode/agents/kb-tech-lead.md`

From `chaos-tester.md:46-53`: Output organized as "Scope and method, Confirmed findings, Assumptions, Limitations." From `project-detective.md:47-57`: Output organized as "Scope and method, What the project is, Structure and components, Entry points, Dependencies, Data flow, Open questions." From `kb-architect.md:52-59`: Output organized by importance (Critical, Important, Suggestions). From `kb-editor.md:51-58`: Output organized by importance (Critical, Important, Suggestions). From `kb-tech-lead.md:54-58`: Output organized by importance (Critical, Important, Suggestions).
- **Explanation**: The assignment-reviewer flagged this as AR-004 (Stylistic). The different formats are appropriate for each agent's purpose but represent a lack of consistency in output structure across the agent ecosystem. A unified format would improve usability when switching between agents.

### AR-005 — Minor — kb-editor's secret detection is heuristic and cannot be verified from static instructions alone

- **File**: `.opencode/agents/kb-editor.md`
- **Evidence** — From `kb-editor.md:36-40`: "* Security considerations: Check for unsafe database practices. Identify exposed credentials, secrets, or sensitive information. Verify that examples follow secure practices such as parameterized queries and least-privilege access." From the Evidence Rules of project-analysis SKILL.md (which govern this review): "Security findings require manual verification unless confirmed by external tooling. Heuristic secret detection produces candidates, not confirmations." From project-analysis SKILL.md:12: "Severity is estimated, never measured. Severity labels are heuristic estimates, not facts."
- **Explanation**: The assignment-reviewer flagged this as AR-007 (which I'm numbering as AR-005 in sequence). The kb-editor agent is tasked with identifying secrets, but from static inspection alone, this cannot be verified. The agent correctly acknowledges this requires manual review, but the finding stands as a limitation of the heuristic approach.
- **Severity**: Minor — A real but limited defect. The agent's capability is constrained by the static-review boundary; users should not rely on the agent alone for secret detection.
- **Recommended fix**: Add an explicit disclaimer to kb-editor.md that secret detection is heuristic and requires manual verification.

### AR-006 — Nitpick — pkm skill mentions `last_audited` but without explicit mandatory requirement

- **File**: `.opencode/skills/pkm/SKILL.md:61`
- **Evidence** — From `pkm SKILL.md:61`: "Set `last_audited` to today's date when creating or editing."
- **Explanation**: The instruction exists but does not explicitly state it is mandatory for all note creations, only "when creating or editing." Reviewers or users might omit the `last_audited` field without violating the written instructions, potentially leading to inconsistent auditing practices. The assignment-reviewer flagged this as AR-005 (Nitpick).
- **Severity**: Nitpick — A trivial preference with negligible impact. The skill functions correctly regardless, but explicit mandatory wording would improve consistency.
- **Recommended fix**: Change "Set `last_audited` to today's date when creating or editing." to "Must set `last_audited` to today's date when creating or editing a note."

### AR-007 — Nitpick — architecture-analysis SKILL.md example doesn't cover responsibility division

- **File**: `.opencode/skills/architecture-analysis/SKILL.md:139-149`
- **Evidence** — From `architecture-analysis SKILL.md:139-149`: The Example section covers **[FACT]**, **[INTERPRETATION]**, and **[INSUFFICIENT EVIDENCE]** labels with an example about API communication, but does not include a specific example about responsibility division.
- **Explanation**: The assignment-reviewer flagged this as AR-006 (Nitpick). The Example section could be more comprehensive; the skill correctly states it should "Clearly identify uncertain areas and information that could not be determined" under Evidence and Limitations, but the example could include a responsibility-division case.
- **Severity**: Nitpick — A trivial preference with negligible impact. The skill functions correctly and the example is not incomplete in a functional sense.
- **Recommended fix**: Add a brief example of responsibility division labeling to the architecture-analysis SKILL.md Example section.
